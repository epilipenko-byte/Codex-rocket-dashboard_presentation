## 4. Data Proxy: проверенная механика

Apps Script должен читать Dashboard Config и источники через Google Sheets API/SpreadsheetApp.

Ключевые правила:

- Не использовать фиксированные позиции строк/столбцов для показателей.
- Метрики искать по названию.
- Нормализовать текст: нижний регистр, убрать пробелы/пунктуацию, заменить `ё` на `е`.
- Использовать fuzzy matching с порогом 72%.
- Не позволять слишком общим словам создавать ложные совпадения.
- Для специальных метрик требовать специфичный токен: например `core`, `influence`, `D/E`, `cash`.
- Отдавать единый `get_all`.
- Сохранять raw-таблицы для вкладок, где пока нет полной нормализации.

## 5. Периоды и месяцы

Период не должен быть зашит до мая.

Правильная логика:

1. Apps Script определяет месяцы из источников.
2. Фронт нормализует месяцы в календарный порядок.
3. Дубли месяцев убираются.
4. Новые месяцы появляются автоматически, если добавлены в источники.
5. Если источник временно не ответил, показывать кэш/резерв, а не демо.
6. Если опубликованный proxy отдает старый формат без `month_keys` и с дублями месяцев, фронт должен построить чистую шкалу по полезному префиксу финансовых рядов и не показывать повторные `Янв/Фев`.
7. Расходные показатели из Google Sheets могут приходить отрицательными. Для P&L-визуализации `var_costs`, `traffic_cost`, `indirect`, `interest`, `dividends` приводить к модулю, а проценты маржинальности пересчитывать из выручки и прибыли.

## 6. Вкладка `Задачи`

Проверенная проблема: `tasks_data` содержит служебные строки сверху.

Правильная логика:

1. Не считать первую строку заголовком.
2. Найти реальную строку заголовков по словам:
   - `Месяц`;
   - `Дата встречи`;
   - `Инструмент`;
   - `Задача`;
   - `Ответственный`;
   - `Дата план`;
   - `Дата факт`;
   - `Статус`;
   - `Результат`.
3. Отображать первые 50 задач и счетчик оставшихся.
4. Статусы определять по тексту статуса и, если возможно, по плановой дате.
5. Не терять длинные описания задач.

## 6A. Raw-таблицы

Для `payment_data`, `ckp_data` и других 2D-массивов нельзя считать первую строку заголовком автоматически.

Правильная логика:

1. Найти строку заголовков по ожидаемым словам конкретной вкладки.
2. Для платежного календаря искать `Месяц`, `Сумма`, `Кошелек`, `Статья`, `Факт`.
3. Для ЦКП искать строку `Период`, чтобы не брать верхний заголовок/описание.
4. Экранировать значения raw-таблиц перед вставкой в HTML.

## 7. Публикация на GitHub

Надежный порядок:

1. Сначала локально проверить файлы.
2. Публиковать в отдельный Codex-репозиторий.
3. После публикации проверить raw URL.
4. Затем проверить GitHub Pages с параметром `?v=timestamp`.

Важный урок: веб-редактор GitHub может показывать изменения, которые фактически не попали в файл, если фокус был не в редакторе кода. После публикации raw-проверка обязательна.

## 8. Дизайн и оформление дашборда

Проверенные решения:

- Темная прозрачная UI-панель поверх живого фона.
- Карточки полупрозрачные, но текст должен быть читаем.
- Вкладки должны быть видны сразу после входа.
- Фон не должен перекрывать интерфейс: iframe с травой должен быть на нижнем слое.
- Фон травы лучше делать как слегка top-down, а не вид сбоку.
- Для плотного финансового интерфейса избегать лендингового hero-стиля.
- Основной экран должен быть рабочим дашбордом, не презентационной заставкой.
- Не использовать слово `DEMO` в рабочей версии.
